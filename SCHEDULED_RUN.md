# Scheduled run rules

This file is the only source of rules for the scheduled task `job-scout-daily-run`, whose SKILL.md only tells the model to read it. The report language is set by the paragraph appended to the end of SKILL.md, and this file does not set one. The stub source is `Scheduled_Tasks/job-scout-daily-run.md`, deployed with `shared/deploy_skills.py` from the Daily_Task repo.

Run the Job Scout local run once in D:\dont_move\git_save\Job_Scout, which really sends the digest mail and pushes the ledger to `origin/data`, then check the output for failures or new issues.

## Rule sources

1. The README describes running Job Scout by hand. Run none of the commands it names, such as `run.py`, a bare `local_run.py` or `merge_seen_jobs.py`, because the closed list below is the only set allowed.
2. Before running, read Pending_fix.md and Known_concern.md at the repo root in full. Both are registers of known defects, kept to suppress repeat reports. Never report anything already registered unless its measured facts changed (fixed, worse, or failing a different way), and in that case name the entry number and what changed.

## Allowed commands (closed list)

Only the two commands below may run during a scheduled run. Command 1 must not change by a single character, and in command 2 only the text inside the `-Message` quotes may change. Neither may gain `&&`, `;`, a pipe or a redirect, or be split or rewritten into another form. Any command outside the list stops at a permission prompt, nobody is there to approve it during a scheduled run, and the whole run hangs. To look at any file, use the Read tool and never assemble a command to read it. Do not run git yourself, not even read-only, since `scheduled_check.py` and `local_run.py` already do every git step and refuse on their own when the checkout is not safe to touch.

1. `conda run --no-capture-output -n ML python "D:\dont_move\git_save\Job_Scout\scheduled_check.py" run`
2. `powershell.exe -NoProfile -File "D:\dont_move\git_save\Daily_Task\shared\notify.ps1" -Message "Job Scout 今日執行發現問題 / 請看排程任務報告" -Title "Job Scout"`

## Running

- Run command 1 with the Bash tool and `run_in_background` set to true, because a scan can outlast the Bash tool's 10-minute foreground limit. Do not poll or sleep while it runs, since any command off the closed list stops at a permission prompt. After starting it, end your turn without writing anything that describes its result. The real completion notification arrives later as its own message, and only then read the output file it names with the Read tool.
- Command 1 first prints a `=== CHECKOUT PREP ===` section. When the checkout holds tracked changes outside the shard dirs it stashes them, and when it is not on `data` it switches there. It then fetches `origin/data` and fast-forwards `data` to it, so `local_run.py` loads the latest code and config. When the fast-forward is not possible it says so, and the scan starts from the local tip, whose code stays loaded even after its own hard-reset brings in the rest. It leaves the checkout alone when a git merge, rebase, cherry-pick, revert or bisect is in progress, when another ledger script holds `local_run.lock`, or when shard files are staged, since the hard-reset would drop their staged state. After the fetch it also refuses when an untracked or ignored file sits at a path that tip tracks, since the hard-reset would overwrite it. `local_run.py` then does not start. Before any of that it parks the GitKraken hand-off, meaning the `gkcommittemplate.*` files and `commit.template`, in `.git/scheduled_check_parked`, because while they exist the commit-msg hook refuses the ledger commit. After taking the ledger lock it refuses to start when that folder is already there, since an earlier run then left the hand-off parked and it needs recovering by hand, as the refusal says. After the scan, or after a prep that stopped partway, a `=== CHECKOUT RESTORE ===` section switches back to the starting branch, restores the stashed changes with their staged state, and puts the hand-off back last. When uncommitted shard rows remain on `data` after the scan, the restore first commits them there and prints a `RESCUED` line naming the commit and the rescue ref. This lets the checkout leave `data` while keeping those rows for recovery.
- Command 1 then prints the start time, the exit code of `local_run.py`, the run's duration, the path and line count of the full log, and a summary. The summary lists every log line that is not INFO, every line without a timestamp (a traceback or a refusal message), and the pipeline milestones such as `fetched=`, `emailed N roles` and `ledger pushed`, each prefixed with its line number in the full log. Two shapes are only counted, `track conflict for` lines (Known_concern.md #4) and `board lists no openings this run` lines.
- The full log is `D:\dont_move\git_save\Job_Scout\ignore_scheduled_run.log`. Read it only when this invocation's output contains the `full output,` line naming it. It can be long, so read the summary first, then use the Read tool with an offset to read the lines around any summary line whose context you need. When this invocation names the log and reports a non-zero `local_run.py` exit code, read the last 200 lines of the log.
- If command 1 ends without printing the `full output,` line, report the failure from the command's own output and do not read the log, because it may belong to another invocation. It ends this way with `local_run.py not started` whenever the prep refused, including when another invocation is still running and holds `local_run.lock`.

## What to check

- Whether command 1 prints `local_run.py exit code: 0`. A non-zero code is a problem. Quote the refusal or the last traceback line. A `local_run.py not started: <reason>` line is the prep refusing, and the reason it names is the one to report. Once the prep has run, the refusal left for `local_run.py` itself is usually commits on `data` that are not on `origin/data`. Report which one it was and do not try to fix it. A refusal means this invocation did not scan, so it always gets the toast, with a message such as `Job Scout 本次未掃描 / 有進行中的 merge / 請看排程任務報告` that names the reason. Do not claim that no other invocation scanned today.
- Any line starting with `RESTORE FAILED` is a problem. Command 1 exits 4 when the scan returned 0 but the restore failed, keeps the scan's own code when that was not 0, and exits 3 when the prep refused. The checkout may still be on `data`, or hold partly restored or conflicted files, and the stash the line names is kept for recovery. Quote the line in the report, including the stash hash and any files it lists, and send the toast with a message such as `Job Scout 改動未完整還原 / 請看排程任務報告`. Do not try to restore anything yourself.
- A `HANDOFF STILL PARKED` line is a problem too. The hand-off was not fully restored, and some of its files may already be back in the git dir. Quote the line and send the toast.
- A `RESCUED` line means the scan failed before committing its ledger rows. It accompanies a non-zero exit code, which is the problem to report, so name the commit and ref it prints in that same item rather than as a separate problem.
- Whether the run reached a mail decision. The summary should hold one of `emailed N roles`, `no new roles this run`, `nothing left to score`, `none left to email`, `all already in the ledger by URL`, `all in suppressed groups`, or `first run: seeded`. A run that fetched but shows none of them is a problem. `no new roles this run`, `all already in the ledger by URL` and `all in suppressed groups` describe new candidates only, and due JD retries can still be scored and emailed after them. So those three alone establish neither a finished mail decision nor zero emailed roles, and the last milestone in the summary is the one that counts.
- Any `email failed` line, and the `run did not catch up` warning from `local_run.py`, are problems. The second means the digest checkpoint did not advance.
- Whether the ledger was pushed, shown by `ledger pushed to origin/data` or `ledger unchanged; nothing to push`. Neither line with exit code 0 is a problem.
- Every remaining WARNING, ERROR or CRITICAL line in the summary. Compare each against the two registers, and count only the ones no entry covers as problems. Lines about a source going dark or a board staying empty for several consecutive runs name a source, so name it in the report.
- Check the `fetched=` line. Report `fetched=0` as a possible fetch-wide failure. For source errors, report newly uncovered failures with the distinct source names and errors. Include the summary's empty-board count, but do not infer that most sources failed or were empty, because neither the summary nor the log provides the total source count.

## Forbidden

- Do not change any code, config, ledger shard or register, and do not stage, commit, push, reset or switch branch.
- Do not write findings into Pending_fix.md or Known_concern.md yourself. List them in the report and let the user decide.

## Report

The first sentence of the report is the conclusion, meaning whether anything is wrong and the confirmed number of roles the digest emailed, or that the email outcome is unknown when the output does not establish it. `emailed N roles` is logged only after the ledger is saved, so its absence does not prove that no mail went out. Then give the `fetched=` numbers and the run's duration when this invocation's output holds them, and say they are unavailable otherwise. When the prep stashed changes or switched branch, say so in one sentence along with whether the restore succeeded. List each newly found problem as a numbered item with its evidence, its cost and where you recommend it go, which is fix now, Pending_fix.md, Known_concern.md, or not yet worth registering.

## Notification

Only when the run fails or finds a new problem, run command 2 **with the Bash tool** to send a toast. Copy it whole and only replace the text inside the `-Message` quotes with one short line saying what the problem is, with no double quotes and no colon in it. The details go in the report.
